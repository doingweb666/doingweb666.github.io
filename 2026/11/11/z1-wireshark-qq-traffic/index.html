【课后作业】用 Wireshark 拆解 QQ 流量：UDP 还是 TCP、加不加密、文件能否还原

date 2026-11-11 • read 11 min • dir 安全工具 #Wireshark #流量分析 #QQ #协议分析
~/posts/z1-wireshark-qq-traffic.md READ-ONLY

教材上讲 QQ 的传输层，标准答案是”UDP 8000，自定义协议”。这次抓了 5 分钟真实流量，22499 个包摆在那里，结论和教材差了整整一代 —— 现在装的 NTQQ 是 Electron 架构，主通道走 TCP 443 + TLS 1.3，另有一条 QUIC over UDP 做低延迟。

这篇文章按作业的三个问题走一遍：是 UDP 还是 TCP、是加密还是明文、能不能从流量里还原出明文文件。

⚙️ 实验环境

项目 内容
抓包机 Windows 11 + Wireshark 4.x（tshark 与图形界面同一套解析器）
客户端 NTQQ（Electron 版，非老版 OICQ 协议）
对端 手机 QQ，与 PC 连同一个 WiFi
抓包网卡 WLAN
抓包时长 300 秒，共 22499 帧 / 7.42 MB

抓包期间的操作：给「文件传输助手」发文字消息、发一张图片、传一个小文件，再用手机发一张图给 PC。

一、开抓之前，先避开三个坑

坑 1：网卡选错，列表全空。

Wireshark 的接口列表里塞了一堆 本地连接* 10、本地连接* 9、蓝牙网络连接 —— 这些是系统创建的虚拟适配器，上面没有流量。选错了就是一片空白，让人误以为 Wireshark 坏了。

先用命令行确认编号再选：

坑 2：显示过滤器会污染统计。

统计 → 会话、协议分级 默认只统计”当前显示的分组”。如果过滤栏里还挂着 ip.addr == 120.233.38.151，打开会话统计只会看到 1 条会话，而不是全部 115 个对端。做统计前先点过滤栏右边的 × 清空。

坑 3：contains 只在当前显示范围内搜。

用 tcp contains ff:d8:ff 找文件头时，如果过滤器里还留着别的内容，等于在一个子集里搜，0 结果毫无意义。

二、整体协议构成：TCP 占九成

统计 → 协议分级：

协议 分组数 占比
总计 22499 100%
IPv4 22238 98.8%
└ TCP 20333 90.4%
└ TLS 7146 31.8%
└ HTTP 83 0.4%
└ UDP 1861 8.3%
└ DNS 578 2.6%
└ gQUIC 843 3.7%
└ QUIC IETF 320 1.4%
IPv6 215 1.0%

5 分钟里平均 75 包/秒，真正承载业务数据的几乎全在 TCP 上，而 TCP 里 每三个包就有一个是 TLS。

UDP 那 8.3% 里，一半是误判

这里有个必须点出来的细节：gQUIC 那 843 个包，看目标端口就知道不对劲 ——

目的地址 目的端口 帧数
106.55.117.183 443 166
10.33.104.90 49228 154
10.33.104.90 65425 121

后两行的目的地址是本机自己，端口是 4~6 万的随机高位端口 —— 这是局域网内的杂项 UDP 广播（发现协议、投屏、P2P 探测之类），被 Wireshark 的启发式解析器猜成了 gQUIC。真正从本机发往腾讯的 QUIC 只有到 106.55.117.183:443 和 116.162.45.56:443 的两条。

启发式解析器的结论要看端口和方向，不能只看协议名列。

三、问题一：UDP 还是 TCP？

两个都在用，但主通道是 TCP。

通道 协议 端口 用途
主通道 TCP + TLS 1.3 443 登录、消息收发、信令、配置下发
实时通道 QUIC（UDP） 443 低延迟数据传输

按端口统计，443 承载了 19668 帧，占全部流量的 87% —— 这个比例基本可以说明一切：QQ 已经把绝大多数业务搬到 HTTPS 上了。

和教材的差异在哪

老 OICQ（教材） NTQQ（实测）
传输层 UDP 8000 TCP 443（+ QUIC/UDP 443）
协议 私有二进制协议 HTTP/2 + TLS 1.3
架构 原生客户端 Electron
加密 应用层私有加密 TLS 1.3 + 应用层私有加密

教材没有写错，只是写的是 2005 年的 QQ。这本身就是流量分析的一个提醒：协议文档永远滞后于客户端，手上的流量才是最新的。

四、把 QQ 的连接单独拎出来

过滤 ip.addr == 120.233.38.151（抓包期间 QQ 的主连接之一），剩 514 个包：

一眼能看出来的：

  • 源端口 61142 → 目的端口 443，固定一条长连接
  • 大量 [TCP Keep-Alive] 和 [TCP Keep-Alive ACK]，心跳间隔稳定在 60 秒左右
  • 中间夹着 TLSv1.3 Application Data —— 真正的业务数据

这条连接从 0.16 秒一直活到 299 秒（会话统计里持续 254 秒），5 分钟的抓包窗口里它始终没断。移动端 IM 靠的就是这种长连接 + 心跳，不然消息推送就得轮询。

清空过滤器再看全局，5 分钟里一共建立了 286 条 TCP 会话，其中 241 条（84%）的目的端口是 443：

大部分会话的字节数在几 kB 到几十 kB，属于短连接 —— 建连、握手、取一次配置或拉一张头像就关掉。真正长期的只有几条：主连接、心跳、以及媒体下载。这种”少数长连接 + 大量短连接”的形态，是典型的长连接 + CDN 混合架构。

五、问题二：加密还是明文？

选中任意一个包，右键 → 追踪 → TCP 流：

整段 8909 字节，149 个包，显示的是可打印字符和 \x 转义混在一起的乱码 —— 没有任何可读的文本、JSON 或字段名。

握手侧的统计更直接：

指标 数量
TLS ClientHello 157
其中首选 TLS 1.3（0x0304） 130（82.8%）
QUIC 连接（TLS 1.3 强制） 320 个包

结论：全程加密，而且是 TLS 1.3。 而且这只是第一层 —— QQ 在 TLS 之上还有自己的应用层加密，登录后协商密钥，消息体再加密一次。就算能在客户端里把 TLS 解掉，看到的仍然是密文。

TLS 1.3 相比 1.2 还砍掉了 RSA 密钥交换和静态 DH，只留 (EC)DHE 前向保密。这意味着抓完包再拿到服务器私钥也没用，解不开历史流量。

六、问题三：能不能还原出明文文件？

作业提示了两条线索：一是不同文件有各自的头部特征码，二是在线传输方式。先用特征码试。

编辑 → 查找分组，选「十六进制值」，输入 ffd8ff（JPEG 的文件头）：

0 个分组。 换成其他格式再试一遍：

特征码 对应格式 命中
ff d8 ff JPEG 0
89 50 4e 47 PNG 0
50 4b 03 04 ZIP 5（来自 113.16.200.76:80，是 Windows 网络连通性检测，不是 QQ）

搜不到，才是正确答案

QQ 的图片和文件不走点对点直传，而是先上传到腾讯云 COS，再由 CDN 分发给接收方，全程 HTTPS。文件的字节流在 TLS 记录里，抓包能看到的只有 Application Data。

会话统计里能反过来印证这一点：

会话 上行 下行 说明
183.195.235.147:443 753 kB 5.8 kB 几乎纯上行 —— 对应”发送图片/文件”
111.29.14.203:443 469 kB 899 kB 上下都有 —— 对应”接收图片/缩略图”

那条 753 kB 的上行会话，方向、大小、时间点都对得上”我把一张图发出去了”，但内容一个字节都看不到。这正是作业里说的”在线传输方式”带来的结果：能证明传了多大、传给了谁（服务器），证明不了传了什么。

七、PC 和手机之间，为什么不直连

我把抓包里所有对端地址去重数了一遍：115 个，全部是公网地址，没有一条连接的对端是私网 IP。

也就是说 PC 与手机之间不存在 P2P 打洞，消息、图片、文件全部由腾讯服务器中转。这也解释了为什么抓包里找不到手机的内网地址 —— 它压根没在这条链路上出现过。

八、加密保护不了的东西：SNI

即使全程 TLS 1.3，握手第一步的 ClientHello 里，SNI 字段仍是明文（除非服务端和客户端都支持 ECH）。从抓包里能直接读出 QQ 连接的后台服务：

SNI 出现次数 用途推测
galileotelemetry.tencent.com 37 遥测上报
work.medialab.qq.com 7 媒体（图片/视频）
otheve.beacon.qq.com 4 信标
rmonitor.qq.com 2 性能监控

更进一步，同一份抓包里还混着这台机器上其他应用的 SNI —— 浏览器、会议、办公、更新服务，全都在列。加密保护的是内容，保护不了”你在连谁”。

这就是流量分析的价值所在：内容看不见，但行为画像依然成立。应急响应里拿到一份 pcap，最先看的往往不是载荷，而是”这台机器在跟哪些域名通信”。

九、三问三答

作业问题 结论 关键证据
UDP or TCP？ 以 TCP 为主（90.4%），辅以 QUIC/UDP 443 协议分级统计；443 端口占 87%
加密 or 明文？ 全程加密，TLS 1.3 为主 157 个 ClientHello / 130 个首选 1.3；TCP 流全是密文
能否还原明文文件？ 不能 搜 ffd8ff、89504e47 均 0 命中；文件走 COS + HTTPS

十、隐私处理

作业要求”注意保护个人隐私信息”，这篇里做了这些处理：

  • 本机地址写作 10.33.104.90（内网私有地址，无法定位）
  • 主机名、用户名、QQ 号、公网出口 IP 均未出现在截图与正文中
  • 抓包中其他应用的域名只做了举例，不展开完整清单

后记

三个问题里，最有意思的不是答案，而是答案为什么和预期不一样：

  1. 教材说 UDP，实测是 TCP —— 说明协议分析不能只背结论
  2. 全加密，但 SNI 明牌 —— 说明”加密”从来不等于”不可分析”
  3. 文件头搜不到，本身就是一条结论 —— 说明搜不到结果时，要先判断是”没有”还是”被藏起来了”

最后补一句工具层面的教训：Wireshark 的协议分级、会话统计都受显示过滤器影响，contains 也只在当前显示范围内生效。做统计之前先清过滤器，否则得到的是子集的统计，还自以为看到了全部。
